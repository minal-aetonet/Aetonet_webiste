Roadmaps often read like wish lists: a sequence of features ranked by whoever argued for them most recently. A roadmap grounded in data looks different—it’s a sequence of hypotheses, each one tied to a metric you were already tracking before you decided to build anything.

Start from the metric, not the feature

Before a feature earns a place on the roadmap, it should be able to answer a simple question: which number moves, and by roughly how much, if this works? If nobody can answer that, the feature is a guess wearing a roadmap’s clothing.

Building a lightweight data foundation

  1. Instrument the funnel first. You cannot prioritize what you cannot measure, and most teams under-instrument the middle of the funnel, not just the ends.
  2. Pick a small number of north-star metrics. Too many competing metrics is functionally the same as having none.
  3. Review the data before the roadmap meeting, not during it. Decisions made live from a dashboard are rarely as good as ones made from a memo.

Important risks to manage

  • Optimizing a metric that doesn’t actually reflect customer value
  • Treating correlation in the data as if it were causation
  • Under-resourcing the analytics work that makes the rest of this possible

A roadmap built this way moves slower on paper and faster in practice—fewer features ship, but far more of them work.
